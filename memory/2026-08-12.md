## Timezone + local-time display for the AQI dashboard (Day 24 scope)

Implemented ONLY timezone/time-display (no AQI tracking / accuracy / DB — later).

Decisions (grill-me Q1 → Option A):
- **Live ticking clock**: `@st.fragment(run_every=30)` around the 4 AQI cards. Key gotcha: fragment args are frozen on capture, so `horizon_times()` is computed INSIDE the fragment body from just the tz name. Context-manager form (`with st.fragment(...)`) is NOT supported on Streamlit 1.61.1 — decorator form only.
- **Horizon semantics**: absolute elapsed hours (`now + timedelta(hours=24/48/72)` in the city's zone, DST-correct via zoneinfo), matching "when 24h from now are completed".

New/changed:
- `src/utils/geo.py`: `resolve_timezone(lat, lon, name=None)` — geocoding name-first (returns tz field, cached), fallback to forecast API `timezone=auto` for any lat/lon (covers quick-pick/GPS/IP).
- `src/utils/local_time.py` (new, pure Python): `horizon_times()`, `format_local_dt()` ("Aug 12, 2026 — 10:10 AM"), `tz_display_name()`.
- `app/components/location_picker.py`: all 4 paths now store `"timezone"` in the location dict (search takes it from geocode result directly).
- `app/components/forecast_cards.py`: `_cards_fragment(tz)` ticking fragment + time footer in each card + tz caption.
- `app/streamlit_app.py`: passes `loc` to `render_forecast_cards(result, loc)`.

Verified with Streamlit AppTest: 0 exceptions, Karachi → Asia/Karachi · UTC+5, cards show Current/+24h/+48h/+72h at local times (e.g. Aug 12 → 13 → 14 → 15, 10:10 AM). All 5 spec cities resolve correctly (Dubai→Asia/Dubai, London→Europe/London, NY→America/New_York, Tokyo→Asia/Tokyo).

Note: `use_container_width` deprecation warnings are pre-existing (app-wide), not from this change.

## Bugfix: Windows crash (reported by AYYAN from PyCharm on Windows)

`ValueError: Invalid format string` at `local_time.py` `format_local_dt()`:
- Root cause: `%-d` in strftime is a **GNU/Linux-only extension**. Windows Python raises ValueError. My Linux tests passed → missed it.
- Fix: build day from `ts.day` (portable). Also added **tzdata** to requirements.txt — Windows Python ships no IANA tz database, so `ZoneInfo()` would raise ZoneInfoNotFoundError there (silent "Local times unavailable").
- Verified: formatter output identical; tzdata makes zoneinfo work with empty PYTHONTZPATH (Windows simulation); full AppTest regression 0 exceptions. Committed+merged as 1a186ea.

## Hopsworks client install on Windows — the real blockers (06:36)

User's base Python is **3.14** (cp314 wheels in pip log). The `imp` error was a
decoy: pip backtracks 5.0.4 → 3.7.0 → 3.4.4 → 3.4.3 because:
1. hopsworks 5.0.4 (ONLY version with a wheel) requires Python <3.14 → rejected on 3.14.
2. 3.4.3's setup.py uses `imp` (removed in Py3.12+) → build crash.
3. Even on supported Python, hopsworks pulls pyjks→twofish; twofish ships NO wheels
   (sdist only, needs C compiler) → fails on Windows without MSVC.

Verified on my Linux box: hopsworks 5.0.4 NEVER imports pyjks at runtime →
`pip install "hopsworks==5.0.4" --no-deps` + manual deps minus pyjks → import OK.
requirements-feature-store.txt now: pins hopsworks>=5.0.4,<6, documents Python<3.14,
and the Windows --no-deps workaround. User must recreate .venv-hs with Python 3.12/3.13.
